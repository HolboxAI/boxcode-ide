# Plan: Two Repos, One Brain

## Thesis

Fork Code-OSS into a JS-native IDE targeting frontend engineers — without rewriting the Rust agent core that already ships PRs today against `HolboxAI/boxcode`. The fork gets a face; the daemon stays the brain.

## Architecture

- **`HolboxAI/boxcode`** (existing, unchanged in kind) — the daemon. Agent loop, tool execution, approval gating. Ships as a spawned task behind a documented protocol once the in-progress `upgrade-plan.md` Phase 3/4 extraction lands.
- **`boxcode-ide`** (this repo) — the face. Fork of Code-OSS, rebranded chrome, a thin TypeScript extension with no agent logic in it, distributed via Open VSX instead of Microsoft's marketplace.
- The two talk over JSON-RPC-over-stdio — the same pattern OpenAI's Codex app-server already proves works across four surfaces (CLI, Desktop, IDE extension, Cloud) from one backend.

Every PR shipped against the Rust core continues to compound into this repo for free once the protocol bridge exists — nothing in `boxcode` gets rewritten to support this.

## Build model for P1 — patch-at-build, not a diverged fork

Confirmed by reading VSCodium's actual build scripts (`github.com/VSCodium/vscodium`), not their marketing: their pipeline does a fresh shallow clone of a pinned upstream `microsoft/vscode` commit **every build**, overlays branding assets, rewrites `product.json` via `jq`, and applies ~69 patch files with `git apply`. There is no permanently-diverged git history to merge — VSCodium's own repo contains only build-script commits, never a merge of VS Code's history.

This is the opposite maintenance model from Cursor's. Cursor maintains a true diverged fork with deep architectural rewrites (core rendering, extension host, for inline diffs and background agents) — that's what forces their dedicated upstream-merge team. **As long as boxcode-ide stays at rebrand-and-repackage (P1–P3 as scoped), the standing maintenance cost is closer to VSCodium's (small, config-driven, patch-repair when upstream's build system shifts) than to Cursor's.** The heavier cost only applies once boxcode-ide starts doing Cursor-style deep core modifications — treat that as a distinct, later decision with its own staffing conversation, not a baseline cost of forking at all.

VSCodium's build scripts are MIT-licensed (confirmed by reading `LICENSE` directly) — legally reusable as the literal P1 starting point rather than building an equivalent from scratch. Naming is centralized in env vars (`APP_NAME`, `BINARY_NAME`, `ORG_NAME`, etc.) substituted into patches via tokens, and the Open VSX marketplace swap is already a clean, reusable patch (`patches/00-settings-gallery.patch`) — most of P1 is plausibly configuration, not new engineering.

## Why this base, not VS Code proper or Zed

- **VS Code fork over building from scratch:** ruled out building a from-scratch editor — both Cursor and Google (via Windsurf's lineage) already validated the fork-Code-OSS path, and Google paid to acquire an existing fork+team rather than build one, which is the closest thing to a market price for how expensive doing this from zero actually is.
- **Code-OSS over Zed:** Zed is Rust-native but GPL-3.0 — using it would mean either open-sourcing boxcode's proprietary layer or keeping the agent core in a separate process talking to a largely-unmodified Zed instance. Code-OSS is MIT, which avoids that constraint entirely, and the target audience (frontend engineers, AWS-not-Azure customers) doesn't need the Microsoft-exclusive slice of the VS Code Marketplace that Open VSX doesn't cover.

## P0 design, grounded in the real code (2026-09-04, revised 2026-09-04)

Read `agent.rs` (727 lines) and `approval.rs` (65 lines) in full rather than guessing at the shape of this. Three things: two already done, one shipped since, one still ahead — and the shape of that last one was wrong on the first pass, corrected below after actually reading `app.rs`.

**Already done (Phase 3 steps 1-2, both merged in `boxcode`):**
- `approval.rs` — a clean typed seam between "the model wants to do X" and "the user decided Y": `ApprovalRequest { call, action, remaining, preview: Option<FileDiff> }` and `Decision::{Allowed, Refused}`. Its own doc comment: *"When the agent loop becomes its own task, these become the messages on the channel between it and the UI."* `preview` already carries the before/after diff — this is P2's "native diff viewer" data, already computed, already there.
- `agent.rs` — the fire→stream→execute cycle already extracted out of `main.rs`'s event loop: `fire_request`, `handle_event`, `execute_approved`, `run_subagent`, each operating on `&mut App` plus an `mpsc::Sender<StreamEvent>`. `StreamEvent` (`Token`, `Reasoning`, `ToolCalls`, `ToolsFinished`, `AgentActivity`, `Usage`, `Done`, `Notice`, `Error`) is already a clean, serializable-shaped enum — already wire-protocol-shaped, just not yet serialized or sent across a process boundary.

**Shipped since (2026-09-04):** `src/protocol.rs` — the JSON-RPC-over-NDJSON wire types (`Notification`, `Request`, and DTOs converted from `StreamEvent`/`ApprovalRequest`/`Decision` via `From`, deliberately kept separate from those internal types rather than deriving `Serialize` directly onto them). 7 tests, schema pinned against literal JSON. Merged, PR #151. This is the *protocol*, not the thing that drives it — see below.

**Still ahead — corrected design, after actually reading `app.rs`'s state machine in full (not just the methods `agent.rs` calls on it):** the first sketch here described this as "wrap `App`'s mutation methods in a trait," which undersold it. `App` doesn't just react to agent events — `advance_approvals`, `decide`, `finish_stream`, `finish_tools` *decide* things (whether to compact, whether a response leaked tool-call markup as prose, when a turn is really over), and they call each other, sharing state (`pending_tools`, `approved_tools`, `messages`, `state: AppState`). A trait per method would fragment one connected machine that needs to stay one thing.

**Real shape:** extract an `AgentSession` struct holding exactly the portable subset of `App`'s ~63 fields (`state`, `pending_tools`, `approved_tools`, `messages`, `mode`, `active_plan`, quota/usage bookkeeping — roughly 15-20 fields), with `advance_approvals`/`decide`/`finish_compaction`/`settle_turn`/`fail_stream` moved onto it **verbatim** (byte-for-byte body, only `self.` → `self.session.` where needed — see the risk note below on why verbatim matters specifically here). `App` holds an `AgentSession` and delegates, then does its own TUI-only work (setting `self.overlay` by inspecting `session.state` after the delegated call, not something `AgentSession` itself does). A new `HeadlessSession` (used by `protocol.rs`'s RPC server) wraps `AgentSession` the same way, converting `state == AwaitingApproval` into a `Notification::approval_request` instead of an overlay.

**One thing that is not portable by refactoring — a product decision, not a technical gap:** `decide`'s handling of a `Deploy` action calls `deploy_takes_over`, whose own doc comment says outright it hands off to the same flow `/deploy` uses because deployment may need "the terminal itself for a browser login." Headless mode needs an explicit policy here before this ships — refuse deploy calls entirely in v1 is the safe default, not something to let get silently stubbed out during extraction.

**Riskiest specific spots, named precisely so a reviewer knows where to look:**
- `decide`'s tail duplicates `settle_turn`'s body inline in one branch (`plan_rejected && state == Sending`) rather than calling `settle_turn()` — extract verbatim; "helpfully" deduplicating this during the move risks silently changing behavior if the two were ever meant to diverge.
- `fail_stream`'s compacting-vs-not branches have the same duplication-not-a-bug pattern.
- `advance_approvals`'s early `return` mid-loop vs. falling through to the post-loop block after it — the control flow depends on that early return specifically skipping the tail. A headless version needs an equivalent "stop and wait for external input" signal at exactly that point, not a refactored loop shape.

**Sequencing:** smallest safe first slice is the `AgentSession` extraction alone (`advance_approvals`/`decide` moved verbatim, `deploy_takes_over`/approval-surfacing left as something `App` supplies and `HeadlessSession` explicitly refuses/auto-declines since there's no UI yet) — full existing test suite should pass identically against `App` afterward, since nothing in the moved logic changes, only its container. Ship and merge that alone before building `HeadlessSession` and wiring it to `protocol.rs`, as a separate second PR — don't combine "extract the struct" and "make it headless-usable" in one change.

## Post-scaffold preview: what Cursor and Codex actually do (2026-09-04)

Follow-up research, prompted by hands-on testing showing both Cursor and Codex surface the running app's UI right after scaffolding a project — before, or without, opening a full code editor. Sourced from official docs/changelogs plus vendor-staff forum posts (this session's web-search budget was exhausted; everything below came from direct fetches, not search).

**The mechanism has a name, and it's Cursor-specific:** a real, named setting, `autoOpenLocalhostUrls` ("Show Localhost Links in Browser," Settings → Tools & MCP). Confirmed by Cursor staff (forum, not docs — this setting is undocumented in the actual docs): it auto-captures any localhost URL the agent's terminal prints into the integrated Browser pane, and per the same staff reply this is *"a separate mechanism for the agents window, doesn't happen in editor window"* — i.e. it's specific to the chat-first Agents Window, not the code editor. It's URL interception, not the agent deciding to open a browser and not the user clicking anything. Default-on is inferred from complaint volume (users asking how to turn it *off*), not confirmed in writing anywhere.

**Codex's "no IDE" is permanent architecture, not a preview mode:** confirmed directly — *"Browser isn't available in Codex CLI or the Codex IDE extension. Open the ChatGPT desktop app to use the built-in browser."* There is no code editor anywhere in the desktop app for a preview to substitute for. Whether it auto-opens unprompted after a scaffold specifically is genuinely unverified either way — could easily be the agent invoking it itself via `@Browser`.

**No vendor anywhere has published a design rationale for "preview before editor."** Checked exhaustively (both vendors' blogs, docs, changelogs, forums). This is unclaimed positioning territory — worth treating as an opportunity to state something neither competitor has, not as a pattern to imitate blindly.

**A real correction to this doc, not just an addition:** the "Onboarding & agent-surface UI" section above describes `vs/sessions` correctly as a real separate native window (confirmed independently, twice) — but it should NOT be conflated with the chat-first landing page. `AgentSessionsWelcomePage` (the `'agentSessionsWelcomePage'` startup editor) is a plain `EditorPane` that renders **inside the normal workbench window**, the same window `browserView` lives in — it is not `vs/sessions`, and not a separate window at all. So "chat-first landing" and "the post-scaffold preview" are both just editor panes in one ordinary window; `vs/sessions` (the Agents Window) is a third, genuinely separate surface, reserved for actual multi-agent orchestration (P4).

**Refines recommendation #4 above, doesn't replace it:** after a scaffold finishes, open `browserView` as a sibling editor pane next to chat, in the *same* chat-first window — not the full code editor, not the separate Agents Window. Cheap, because both panes already exist as siblings in one workbench. Concrete implementation details the research surfaced, not guessed:
- **Gate on the dev server actually responding**, not on the printed URL line — poll the port before opening. Cursor users report seeing connection-refused pages from skipping this.
- **Restrict auto-open to localhost URLs from servers the agent itself started this session.** Cursor's actual user complaints are about *over-broad* interception hijacking unrelated links (PR/GitHub URLs opening in a browser with no auth cookies) — don't repeat that.
- **Ship it as a documented, named, default-on toggle** (mirror `autoOpenLocalhostUrls`'s existence, not its lack of documentation), with a one-keystroke escape to the real editor.

**A landmine for whoever builds this:** `patches/00-ui-custom-font.patch` deletes `AgentSessionsListDelegate.ITEM_HEIGHT`/`SECTION_HEIGHT` (replaced with `FONT.*` tokens) — new pane-layout code referencing the old constant names won't compile.

A macOS dmg build was running while this was written — nothing below depends on it, and the honesty section at the end says exactly which claims it would settle.

**The bug fixes are the strongest work in the batch, and should be read as the template.** PR #32 (`patches`-free, in `src/stable/extensions/boxcode-agent/src/cdpClient.ts`) found that `CdpClient.send()` had no timeout at all, so a backgrounded tab that never produced a compositor frame for `Page.captureScreenshot` left the promise permanently unsettled — not rejected, never resolved. `boxcode` PR #161 independently bounds the other side (`src/headless.rs`, `BROWSER_CHECK_TIMEOUT = 90s` around the oneshot) and correctly labels itself defense-in-depth rather than the fix. PR #33 traced the disappearing-browser-tab symptom to `agentSessionsWelcome.ts`'s `closeEditorAndMaximizeAuxiliaryBar` being both the landing-page transition *and* the body of `openSessionInChat` (wired to `onDidSubmitRequest`), so it re-maximized — and therefore `setEditorHidden(true)` — on every message. ### Correction: element-selection-to-chat is **not** substantially shipped

`docs/BACKLOG.md`'s Tier 2 item anticipated that PR #30 would deliver this. Reading the merged diff, it does not — and the gap is precisely the part that matters.

`attachReferencesToPrompt()` (`src/stable/extensions/boxcode-agent/src/extension.ts`) folds `request.references` into the plain-text prompt, but explicitly counts every `vscode.ChatReferenceBinaryData` into `skippedImageCount` and tells the user *"boxcode can't take image input yet."* The element **screenshot** is the feature; the CSS path and `outerHTML` are the consolation prize. Console-log-to-chat does survive (it is text), and the honesty of surfacing the skip rather than silently dropping it is correct behavior — but the Tier 2 row should read *partially shipped*, not shipped.

**The root cause is one enum, and the fix is much cheaper than it looks.** `src/protocol.rs:285` in `boxcode` defines `ContentBlock` with a single `Text` variant, deliberately (its own doc comment cites ACP v1's baseline obligation), and `src/transport.rs:381-387` fans the prompt in over exactly that one arm. But the multimodal path already exists on the outbound side: `src/llm.rs:172` already emits an `ImageUrl` content block, and PR #159 already feeds `check_in_browser`'s screenshot back to the model as vision context. So the model can already see images — nothing about the LLM layer needs building. What's missing is an inbound `ContentBlock::Image` variant, the matching `PromptCapabilities` advertisement, and deleting the skip branch in `extension.ts`. That converts a half-shipped headline feature into a real one for roughly the size of PR #159. **Sequence it ahead of any further visual polish.**

**A real defect in the same function, unrelated to images:** for any reference that is neither a string nor binary data, it does `String(reference.value)`. `vscode.d.ts:19846` types that field as `string | Uri | Location | unknown`. `Uri` stringifies fine; a `Location` (`{uri, range}`) stringifies to `[object Object]`, which would be injected into the prompt as if it were context. Worth a narrow follow-up that switches on the shape.

### The visual layer: one real lever, two half-levers

The brief for this review asked directly whether "premium" landed or is surface-level. Honest answer: **not yet — but the instincts are right and the remaining work is small and specific.**

**1. The amber accent regresses contrast on the most-clicked surface in the product. This is arithmetic, not taste.**

`boxcode-dark.json` / `boxcode-light.json` set `button.background` (and `activityBarBadge.background`, and `menu.selectionBackground`) to `#D97706`. None of them touch the paired foreground, which stays `#FFFFFF` in both stock themes (`extensions/theme-defaults/themes/dark_modern.json:12,17`; `light_modern.json:12,17,67`). Computed WCAG 2.1 contrast ratios:

| pair | ratio | AA normal text (4.5:1) |
|---|---|---|
| `#D97706` on `#FFFFFF` (boxcode, both themes) | **3.19:1** | **fails** |
| `#0078D4` on `#FFFFFF` (upstream Dark Modern) | 4.53:1 | passes |
| `#005FB8` on `#FFFFFF` (upstream Light Modern) | 6.31:1 | passes |
| `#B45309` on `#FFFFFF` (boxcode `button.hoverBackground`) | 5.02:1 | passes |
| `#D97706` on `#000000` | 6.59:1 | passes |

So every primary button, activity-bar badge and selected menu row went from passing to failing, in both themes — and the button becomes *more* legible on hover than at rest, which is backwards. This is the classic amber-600 trap: amber is a light hue and does not carry white text. Two cheap fixes, either works: set the paired foregrounds to `#000000` (6.59:1, keeps the brand hue exactly), or move the resting background down to `#B45309` and the hover to `#92400E`. The theme files already demonstrate the authors know how to do this — `textLink.foreground` was deliberately darkened to `#92400E` in the light theme (7.09:1) with a comment explaining exactly this reasoning. The buttons just didn't get the same pass.

**2. Is amber-on-warm-neutral actually distinctive, or just fine? The accent is distinctive; the palette isn't a palette yet.**

The accent choice is genuinely unclaimed — the category is saturated with blue (Copilot, Zed), monochrome (Cursor), and green (Windsurf); nobody owns amber. Keep it. And the surface-elevation work in PR #34 is the single most sophisticated instinct in the whole batch: `editorWidget.background: #211F1C`, `input.background: #302C27`, `dropdown.background: #332F29` are warm-biased rather than flat gray, and the patch comment is right that a slight hue bias toward the accent is what reads as elevation.

But that instinct touches **3 keys out of ~230** in `COLOR_THEME_DARK_INITIAL_COLORS`. The editor background, side bar, activity bar, panel, tab bar, list hover and every border are still stock Dark Modern neutral gray. The current result is warm widgets and an amber accent floating on a cold gray ground — which reads as *stock VS Code with a brand color*, not as a designed surface. That is the honest verdict on "premium": the theme is currently **fine + distinctive accent**, not premium. Closing that gap is not a large job — it is extending the same warm-bias rule already applied to three keys across the ~15 large-surface backgrounds and borders, in both themes, and checking it against the token contrast requirements above. Do that before adding any more visual features; it is higher leverage per hour than anything else in the visual bucket.

**3. The corner-radius bump is safe to apply but does not do what the patch claims, and is currently half-migrated — the worst of the three states.**

`patches/91-ui-rounded-corners.patch`'s own comment says 85 CSS files read these tokens, "so retuning it here reaches all of them at once instead of hand-patching each file." Measured against the pinned tree, that overstates the reach substantially:

- Across `src/`: **254** `border-radius` declarations use `var(--vscode-cornerRadius-*)`; **525** are hardcoded values. The token covers about a third.
- The largest single remaining bucket is **128 literal `border-radius: 4px;`** declarations (plus 4 unspaced and 10 directional `4px` variants), and **41** at `6px` — i.e. precisely the two values the patch moved the tokens *away from* (`small` 4→5, `medium` 6→8).
- In the chat UI specifically — the surface the patch names as its main justification — only **33 of 212** `border-radius` declarations under `src/vs/workbench/contrib/chat/` use the token. The other 179 are hardcoded. Reach there is ~16%, not "all of them."

PR #35 migrated exactly 3 of the 525 outliers (`button.css`, `inputBox.css`, `dropdown.css`). So the net effect is not a systemic softening — it is that surfaces which previously *matched* their hardcoded neighbours at 4px and 6px now differ from them by 1px and 2px. **The risk here is incoherence, not breakage**, and it is exactly the class of regression that source-reading cannot see and a running build shows immediately.

One second-order effect worth eyes specifically: `.monaco-button` moved from a hardcoded `4px` to `cornerRadius.medium`, which is now **8px** — a doubling — on a control whose padding is `4px 8px`. On a short button that geometry reads as a pill rather than a rounded rectangle. Same doubling applies to `inputBox.css`.

Recommendation: pick one of two coherent end-states, not the current middle. Either (a) finish the migration — sweep the 128 literal `4px` declarations onto `cornerRadius.small` and the 41 `6px` onto `cornerRadius.medium`, which is mechanical and makes the token genuinely systemic; or (b) revert `cornerRadius.small` to 4 and keep only `medium`/`large`/`xLarge` bumped, which minimizes the mismatch surface. (a) is the better product answer and is a contained afternoon; (b) is the safe answer if the dmg shows the mismatch is visible.

**4. Geist is defensible, but the PR framing contains one factual error and one unresolved build risk.**

Defensible on the merits: leaving `editor.fontFamily` untouched is the right call and the patch says why. Forcing a code font is the most-reverted opinionated default an editor can ship, and chrome-vs-code is a real distinction — Geist for chrome, the developer's own mono for code, is exactly how Vercel themselves use it. Licensing is clean (SIL OFL 1.1, `OFL.txt` bundled). Keep the choice.

**Correction to the PR's own framing:** these are not "VS Code's existing but previously-unused settings." `workbench.experimental.fontFamily` and its five siblings do **not exist** in the pinned upstream commit — `grep -rn "experimental.fontFamily" src/` against `7e7950df8` returns nothing, and `src/vs/workbench/browser/workbench.contribution.ts` (1058 lines there) contains no `fontFamily` at all. The hedge costs nothing and loses nothing: use `format("woff2")` — a variable font is served correctly under the plain hint, and `font-weight: 100 900` on the same rule already declares the variable axis range.

## Re-examined 2026-09-05: is predictive "Tab" completion still the #1 gap?

`docs/BACKLOG.md`'s Tier 2 list has ranked predictive multi-line completion as *"the single most-loved, most 'wow factor' feature in user sentiment research across competitors"* since it was added. That claim carries **no research date in the doc**, which is itself the problem — it has been treated as settled ever since. It was challenged directly during this review on the grounds that it may be stale: line-by-line completion is a pre-agentic interaction model, and 2026 is dominated by agentic multi-file workflows. That is a fair challenge and it was re-researched rather than defended.

**Verdict: the ranking was overstated, but the feature is not obsolete. Downranked from "#1 gap" to "table stakes — build it, don't lead with it."** Three findings support that, and the third one changes the cost calculation enough to matter on its own.

**1. Sentiment in 2026 is genuinely three camps, not two.** The obvious framings — "Tab still matters" vs. "agents replaced it" — both appear, but the most common 2026 position is a third one: *agents aren't good enough yet, so Tab covers the gap.* Representative and dated:
- nurumaik, 2026-06-16: *"agentic coding is still lacking... cursor tab helps a lot with boring parts"* — [HN 48562699](https://news.ycombinator.com/item?id=48562699)
- toyetic, 2026-04-03: *"I've mostly switched to claude code (using the intellij plugin)... But I will say the one thing i miss is the tab autocomplete cursor has"* — [HN 47629894](https://news.ycombinator.com/item?id=47629894)
- turastory, 2026-05-19: *"Cursor's tab completion is still the best I've used"* — [HN 48190863](https://news.ycombinator.com/item?id=48190863)

Strategically this is the important nuance: **if some of today's Tab demand is a hedge against agent quality, that demand shrinks as agents improve.** That argues hard against a bespoke in-house model program and hard for the cheapest credible implementation.

**2. Tab is not what 2026 churn is actually about — in either direction.** In the "Cancelling Cursor" discussion, essentially none of the stated cancellation reasons are Tab-related; they are cancellation-flow friction (*"I lost count of how many screens...I had to click through"* — [HN 49147480](https://news.ycombinator.com/item?id=49147480)), acquisition/ownership backlash, and general enshittification. People are not leaving because Tab got worse, and they are not leaving because Tab became obsolete. **Nobody is churning over Tab.** That is the single strongest argument for downranking it: it does not behave like a retention lever. It behaves like a thing whose absence is noticed.

The counterweight, and the reason it stays on the list rather than coming off: toyetic's profile above — a developer who has largely moved to an agent, still misses Tab, and is shopping — is very close to boxcode-ide's actual target user. We do not need to beat Cursor Tab. We need to not be the tool where it is conspicuously missing.

**Two things stated as unverified rather than dressed up.** (a) No 2026 comment was found that establishes *"I disabled Tab because it fights my agent"* — that hypothesis was looked for specifically and not confirmed. (b) The whole sentiment corpus above is Hacker News only; r/cursor and X, the two highest-volume venues for exactly this question, were unreachable within budget. One dissenting datapoint worth recording precisely because it cuts against the older consensus: hypercube33, 2026-02-17, *"Weirdly I actually hate tab complete in Cursor but love it with GitHub Copilot"* — [HN 47047171](https://news.ycombinator.com/item?id=47047171). One comment; don't over-read it.

**3. The build cost is far lower than this doc has ever assumed, and this was verified directly against our own pinned checkout, not taken from research.** The expensive part of Tab is not the model — it is the rendering and interaction layer (ghost text, multi-line diff previews, cursor-jump affordances, accept/reject/partial-accept, keybinding arbitration against IntelliSense). **All of it is already in MIT-licensed VS Code core, in our tree, untouched by any patch:**

- `src/vs/editor/contrib/inlineCompletions/` — **68 TypeScript files**, split into `browser/model`, `browser/controller`, `browser/hintsWidget`, and two renderers: `browser/view/ghostText` (classic inline completion) and `browser/view/inlineEdits` (the Copilot-NES-style rendering, with its own `inlineEditsViews/`, `components/`, `theme.ts` and `view.css`). Header confirms `Licensed under the MIT License`.
- The extension-facing API is **stable, not proposed**: `vscode.languages.registerInlineCompletionItemProvider` (`src/vscode-dts/vscode.d.ts:14862`), `InlineCompletionItemProvider` (:5233), `InlineCompletionItem` (:5326).
- The next-edit-suggestion behaviour specifically is opted into via `vscode.proposed.inlineCompletionsAdditions.d.ts` — `isInlineEdit` (:39), `showInlineEditMenu` (:47), `displayLocation` (:57). `extensions/boxcode-agent/package.json` already enables four proposed APIs, so adding a fifth is one line in a mechanism we have already proven.
- `editor.inlineSuggest.enabled` **defaults to `true`** (`src/vs/editor/common/config/editorOptions.ts:4539`), so no patch and no settings change is needed to light the surface up.
- **Copilot's NES is a *provider*, not the machinery.** `extensions/copilot/src/extension/inlineEdits/vscode-node/inlineEditProviderFeature.ts` and `jointInlineCompletionProvider.ts` register into exactly the core APIs above — and `patches/52-ext-copilot-remove-it.json` deletes the entire `extensions/copilot` directory. Net: in boxcode-ide today, the inline-completion surface is **live with zero providers registered**. `grep -l inlineCompletions patches/*` returns nothing; core is pristine.

**And it is better than that — the historic core-vs-closed-extension split has collapsed, and the reference *provider* is MIT in our tree too.** `microsoft/vscode-copilot-chat` was archived 2026-05-20 and development moved into the main repo; our pin postdates that. Verified directly: `extensions/copilot/LICENSE.txt` opens `MIT License / Copyright (c) Microsoft Corporation`. That directory contains a complete, production, shipping next-edit provider we are legally free to read and adapt with attribution:
- `extensions/copilot/src/extension/xtab/` — prompt crafting, diff-history assembly, response handlers, a separate next-cursor predictor. The prompt vocabulary is in `xtab/common/tags.ts`: `<|cursor|>`, `<|code_to_edit|>`, `<|area_around_code_to_edit|>`, `<|current_file_content|>`, `<|edit_diff_history|>`, `<|recently_viewed_code_snippets|>`.
- **The token budgets are the single most useful number in this research, because they are far smaller than intuition suggests** (`platform/inlineEdits/common/dataTypes/xtabPromptOptions.ts`, `DEFAULT_OPTIONS`): current file 1,500 · recently viewed 2,000 across 5 documents · diff history 1,000 across 25 entries · edit window 2,000 — **~6.5K tokens total**, against a 12,285 prompt cap. This is a shipping production config, not a demo. **Do not over-engineer context.**
- `extensions/copilot/src/extension/typescriptContext/` — a **90-file** (verified count) TypeScript language-server plugin doing TS-aware context extraction for NES, with its own `serverPlugin/fixtures/nes`. For an IDE positioned at frontend engineers this is the most on-target single asset in the entire tree.
- A **BYO-endpoint path already exists and is first-class**: `github.copilot.chat.advanced.inlineEdits.xtabProvider.url` / `.apiKey` (`configurationService.ts:787-788`), plus a `CUSTOM_NES` model id. That makes a same-day latency/prompt-format spike possible before committing to anything.
- **Legal boundary, stated so nobody trips over it:** the *code* is MIT and reusable with attribution. The "GitHub Copilot" name and branding, the CAPI endpoints, and the auth/entitlement flow are **not**. Any reuse must be rebranded and pointed at our own endpoint.

**The proposed-API gate is a one-line change we already own.** Core reads the allowlist from `product.json` (`src/vs/workbench/services/extensions/common/extensionsProposedApi.ts:43`), and our `product.json` already allowlists `inlineCompletionsAdditions` for six extension IDs (lines 83, 248, 252, 293, 389, 392 — verified). Adding `boxcode-agent`'s id is one entry.

So the honest scoping is: **we do not build Tab. We register a provider, copy a published prompt shape, and point it at a model.** Recommended path is a thin extension of our own (~1–2 weeks) rather than repointing or forking Copilot's: register `registerInlineCompletionItemProvider`, return `isInlineEdit: true` plus `jumpToPosition` (and `uri` for cross-file), allowlist the id, and let core render ghost text, side-by-side diff, gutter indicator, collapsed mode, Tab-to-jump and the long-distance hint. **It requires no fork-layer patching at all**, which keeps it inside the cheap VSCodium-style maintenance model described in "Build model for P1" above.

**The genuinely hard remaining problem is model quality and latency — and there is a published, credible recipe at our scale.** Zed's Zeta 1 shipped in a real product trained on roughly **550 hand-curated examples** (418 SFT + 132 DPO), with the dataset (583 rows, Apache 2.0) and the SFT/DPO notebooks public; the ~100k-example scale-up came *after* shipping, distilled from their own production traffic. Zeta 2.1 is 8B, Apache 2.0, and purpose-trained for next-edit — the only open model that is. For plain FIM, Qwen2.5-Coder (Apache 2.0, 0.5–32B) is the cheap default. **Codestral is a trap and should not be planned around**: the open 22B weights are non-commercial (MNPL), the current model is proprietary, and `codestral-2501` was retired 2025-11-30.

Published latency reference points, all vendor-measured: Zed targets p50 <200ms / p90 <500ms; Zeta 2 hit 189/401ms at ~270 output tokens; **Zeta 2.1 hit 136/350ms at ~90 output tokens**; Cursor went 475ms p50 → 260ms p50 while more than doubling context when it fused jump prediction into one model. **The dominant lever is output tokens, not a faster model** — Zeta 2.1's win came from emitting only changed regions. **Design the output format before picking the model.**

Three build decisions that follow directly, recorded now so they aren't rediscovered:
1. **Fuse cursor-jump into the single model rather than running a separate predictor.** Cursor fused (and cut p50 latency nearly in half doing it); GitHub kept `xtabNextCursorPredictor.ts` separate. Two sequential model calls is the obvious latency trap.
2. **Build one unified provider, not two.** Core at our own commit contains `inlineCompletionsUnificationState` in the proposed API — commented *"temporary: to be removed"*, carrying `expAssignments` — i.e. a live A/B experiment merging ghost-text completion and NES into one model and one provider, consumed by `jointInlineCompletionProvider.ts`. Building two separate providers means building toward an architecture upstream is actively dismantling.
3. **Ship an eagerness control from day one, and keep Tab out of the agent's lane.** The complaint axis on Tab is *intrusiveness, not incompetence*, and it is bimodal — the same feature is the sole reason one user stays and the sole thing another disables. Core already provides `editor.inlineSuggest.edits.showCollapsed` and `minShowDelay`; GitHub shipped a user-facing "NES eagerness" control in v0.38 (2026-03-05). Be aggressive on sub-line edits and conservative on large rewrites: the documented user mental model is *"more than a word or two → that's the agent's job."*

**Vendor-investment evidence behind the "table stakes, not differentiator" verdict, since it is the half that isn't sentiment.** Marketing has moved wholesale to agents while engineering has not: cursor.com's homepage does not mention Tab anywhere (headline: *"Cursor is your coding agent for building ambitious software"*), cursor.com/pricing mentions no completion tier, and neither cursor.com/blog (Jul–Sep 2026) nor cursor.com/changelog (2026-08-13→09-02) carries a single Tab entry — the last Tab engineering post is [cursor.com/blog/tab-rl](https://cursor.com/blog/tab-rl), **2025-09-12**. VS Code's own release notes for both 1.126 and 1.136 mention NES zero times. Windsurf's Tab docs now 307-redirect to `docs.devin.ai/desktop/tab`; Augment Code deprecated completions for all non-Enterprise plans on 2026-03-31.

But the engineering never stopped. Zed published four dated edit-prediction posts in 2026 ([edit-prediction-providers](https://zed.dev/blog/edit-prediction-providers) 2026-02-04, [zeta2](https://zed.dev/blog/zeta2) 2026-03-25, [how-we-developed-zeta2](https://zed.dev/blog/how-we-developed-zeta2) 2026-04-07, [zeta2-1](https://zed.dev/blog/zeta2-1) 2026-05-08) and **monetizes it** (free plan capped at 2,000 predictions/month). And `extensions/copilot/CHANGELOG.md` in our own tree records v0.38 (2026-03-05) shipping *"Long-distance next edit suggestions — NES now predicts and suggests edits anywhere in the file, not just near the cursor"* plus the eagerness control, and v0.35 (2025-12-10) shipping a new NES model. Cursor's last published scale figure is **400M Tab requests/day** (2025-09-12, vendor).

**That split is the verdict in one line: nobody sells Tab any more, and nobody has stopped building it.** Which is exactly what "table stakes" means.

**Research limitations on this section, stated rather than buried.** The web-search budget was exhausted before this research began, so every external claim came from a direct fetch of a named URL with no discovery search — **absence of evidence here is not evidence of absence**, and the "no Tab entries" findings come from single un-paginated pages. There is no data on Copilot NES releases Apr–Jun 2026 (the bundled changelog stops at v0.41 while the shipped `package.json` is 0.54.0 — do not read that gap as inactivity). Windsurf/Devin Tab publishes no metrics at all and two of its blog URLs returned HTTP 429. Zeta 2/2.1 context windows, StarCoder2's FIM sentinels and JetBrains' model size are all UNVERIFIED. Everything in section 2 above, by contrast, was verified by direct file read against our own checkout and is the most reliable material here.

**Consequences for sequencing, stated against the existing rationale rather than overriding it silently:** BACKLOG's instruction was *"Rank this at least alongside inline-edit, not below it."* That instruction is kept — inline-edit and Tab are the same core subsystem and should be one workstream, which the original entry did not know. What changes is the ranking *against everything else*: it moves off "#1 gap" because no evidence shows anyone churning over it, and because the frontend-specific browser/visual loop (below, and Tier 3) is where this product's actual differentiation lives. Build Tab because its absence is conspicuous and it is now cheap — not because it wins anyone.

## Retention research 2026-09-05: what actually makes a frontend engineer stay

Commissioned to answer a specific question, not to produce a feature checklist: *once a frontend engineer is onboarded, what stops them leaving?* Sourced from the Hacker News Algolia API, direct vendor changelog/blog fetches, and named developer blogs.

**Read the method caveats before citing any of this.** They are real limitations, not boilerplate: **Reddit was unreachable** from the research environment (r/cursor, r/ChatGPTCoding, r/webdev contributed *nothing* — and that is exactly where the "why I left X" genre lives), X/Twitter likewise, and **openai.com returns HTTP 403** to every fetch, so OpenAI's own posts are cited by URL and third-party discussion only, never by content claimed as read. Thread IDs, usernames, dates and point counts came from the Algolia JSON directly and are reliable; **quote strings passed through a summarizing fetch layer and should be spot-checked at their permalinks before anything here is repeated outside the team.**

### The five things that determine retention, ranked, with evidence strength stated

**1. Predictable, legible cost. This is the #1 churn trigger by a wide margin — and it is not what this plan has been optimizing for at all.** *Evidence: strong.* Every vendor studied triggered its largest public backlash on a pricing or rate-limit transition, not on output quality. Cursor's June 2025 change forced a formal apology — ["Clarifying our pricing"](https://cursor.com/blog/june-2025-pricing), 2025-07-04: *"Our recent pricing changes for individual plans were not communicated clearly, and we take full responsibility"* — plus refunds for a named window. GitHub Copilot's move to usage-based billing ([github.blog](https://github.blog/news-insights/company-news/github-copilot-is-moving-to-usage-based-billing/), 2026-04-27) drew **767 points / 553 comments**, with derkoe documenting *"some 900% raises... Sonnet 4.6 from 1x to 9x, Opus 4.6 from 3x to 27x"* ([HN 48007428](https://news.ycombinator.com/item?id=48007428)) and darqis the felt version: *"Your 300 messages became 50 or your 1500 became 250 per month"* ([HN 47935360](https://news.ycombinator.com/item?id=47935360)). AWS Kiro capped usage within a week of launch; Windsurf's economics contributed to its collapse.

The consistent shape: **the anger is about the transition and the opacity, not the absolute number.** And the two live bets are visibly opposed — Cursor removed cost detail from its usage page in Aug 2026, while Claude Code shipped prompt-cache-miss cost diagnostics in `/cost`. The market punished the first.

*Why this matters here specifically:* boxcode's closed, fixed tool set means we control the token budget end to end. That is an **advantage** for this, not merely a constraint — we can show a truthful per-turn cost meter that a tool built on arbitrary third-party MCP servers structurally cannot. This is the cheapest retention insurance available to us and it is currently nowhere in P0–P6 or any Tier.

**2. A verification loop that is cheap in context — not merely present. This is the sharpest opportunity in the whole report, and it materially corrects this doc's framing of the browser work.** *Evidence: strong.* "The agent can't see the page" is the most-repeated frontend complaint — Adam Argyle (ex-Chrome DevRel), ["Why AI Sucks at Front End"](https://nerdy.dev/why-ai-sucks-at-front-end), 2026-04-12, section headings *"It's an LLM, not a rendering engine!"* and *"It literally cannot see"*; PaulHoule: *"they're blind as a bat and don't understand how things stand visually"* ([HN 47739434](https://news.ycombinator.com/item?id=47739434)).

**But — and this is the correction — the market objection is not "nobody has this."** Playwright MCP, Chrome DevTools MCP and Antigravity's Browser Control all exist, and commenters say so immediately and dismissively (mohsen1: *"playwright can do all of that too. I'm confused why this is necessary"* — [HN 47500183](https://news.ycombinator.com/item?id=47500183); m00dy: *"Gemini on Antigravity is already doing this"* — [HN 47500293](https://news.ycombinator.com/item?id=47500293)). The genuinely unsolved parts are exactly two, both well-attested:
- **The loop burns context faster than it earns.** boomskats: *"chrome devtools mcp really clutters your context. Playwright-cli (not mcp) is so much more efficient"* ([HN 47500807](https://news.ycombinator.com/item?id=47500807)). hamasho: *"it takes a lot of time to complete even easy tasks... each step requires dozens of DOM analyzes and actions"* ([HN 48031468](https://news.ycombinator.com/item?id=48031468)).
- **DOM assertions don't catch visual wrongness.** mrothroc, the sharpest articulation in the corpus: *"Playwright checks structural properties, like does element X exist, is it visible... but it can't tell you whether the page actually looks right... Colors wrong, layout shifted, spacing off, components overlapping"* ([HN 47504657](https://news.ycombinator.com/item?id=47504657)).

**This is the one place where the closed fixed tool set is a genuine technical advantage rather than a business preference**, and it is a defensible claim rather than a marketing one: controlling both ends of the protocol lets a first-party browser tool ship a purpose-built, token-efficient page representation that a generic MCP server cannot. **Positioning follows directly: "verification that doesn't eat your context window," not "our agent can see."** The second claim is already commoditized, and Cursor took **724 points / 309 comments** of public beating in Jan 2026 for over-claiming exactly it — ["Cursor's latest 'browser experiment' implied success without evidence"](https://news.ycombinator.com/item?id=46646777), where josefritzishere's *"This is what most AI 'successes' turn out to be when you apply even a modicum of scrutiny"* is the tone to avoid earning.

**3. Trust — in the agent's blast radius and in the vendor's intentions.** *Evidence: strong for the negative case.* Trust failures produce the highest-engagement threads in the dataset and, unlike pricing anger, they appear **terminal**. Antigravity alone: [data exfiltration via indirect prompt injection](https://www.promptarmor.com/resources/google-antigravity-exfiltrates-data) (768 pts), ["deleted the contents of whole drive"](https://news.ycombinator.com/item?id=46103532) (544 pts), [a forced auto-update that destroyed chat history and settings](https://www.0xsid.com/blog/antigravity-bait-n-switch) (771 pts), and TOS terms letting third-party usage suspend your whole Google account ([HN 49548452](https://news.ycombinator.com/item?id=49548452), 333 pts, this week).

**The asymmetry is the finding: users came back to Cursor after a pricing scandal; nobody in this corpus describes returning to Antigravity after a trust incident.**

*Directly load-bearing for our bundling strategy, and the reason this belongs in the plan rather than in a footnote:* a bundled DB/auth/deploy stack asks for far more trust than a plain editor. Lovable is the exact warning shot — allthetime: *"The supabase backend is completely inaccessible except through the lovable interface. You don't have a supabase account, you can't manage any of it directly"* ([HN 49288290](https://news.ycombinator.com/item?id=49288290)), and a week later *"wildly over-priced, under powered, and has crazy levels of lock in built in"* ([HN 49402474](https://news.ycombinator.com/item?id=49402474)). **This is not an argument against the bundling strategy and is not offered as one** — the strategy is settled. It is a specific execution constraint on it: *bundle the convenience, never bundle away visibility or the exit.* Ship read access to the real DB and a working export from day one. The rage Lovable earns is not for locking users in; it is for making their own data unviewable.

**4. One irreplaceable daily-use primitive — the only proven non-model moat in the entire corpus.** *Evidence: moderate — consistent, but a small number of voices.* This is where the Tab research above and this research meet, and they need reconciling rather than averaging.

Everything else in these products proved substitutable within months. Bundled features are copyable (Cursor shipped its own code hosting in Aug 2026; Kiro's spec workflow was reimplemented for free by the community). And **the model layer cannot be a moat — it can be removed by a third party with a blog post**: Anthropic cut Windsurf's Claude access in June 2025 (*"it would be odd for us to sell Claude to OpenAI"*), and OpenAI published a decision to cut Cursor's access after the SpaceX acquisition ([openai.com](https://openai.com/index/our-decision-on-cursor-following-its-acquisition-by-spacex/), 2026-08-29, 852 pts — ⚠️ **the specific cutoff date and rationale circulating in that thread are UNVERIFIED; the primary source 403'd on three attempts. Read it manually before repeating.**).

Against that, inline completion is the single clearest case of something holding users **against a better model elsewhere** — wellthisisgreat concedes the point explicitly: *"Cursor's TAB is too good to give up vs Roo / Cline. I do agree Claude's the best for programming"* ([HN 44282995](https://news.ycombinator.com/item?id=44282995), 2025-06-15). Corroborating, from separate comments: mjrbrennan, *"the Cursor Tab autocompletion is still the best AI-based editor autocomplete I have used"* ([HN 48564945](https://news.ycombinator.com/item?id=48564945)) and *"I switched to VSCode and the only thing I miss is cursor tab"* ([HN 48702979](https://news.ycombinator.com/item?id=48702979)); komali2, *"I desperately wish there was a package... matched the multiline, file-aware autocomplete feature of Cursor"* ([HN 45126726](https://news.ycombinator.com/item?id=45126726)); ddxv, *"I recently canceled CoPilot to go back to Cursor, it's just so much faster for the inline code completion"* ([HN 45829159](https://news.ycombinator.com/item?id=45829159)).

**Reconciling this with the Tab section above, which downranked it — the two findings are not in conflict, and the synthesis is sharper than either alone.** Nobody churns *over* Tab (no 2026 cancellation thread attributes leaving to it, in either direction). But Tab is the only documented instance in this corpus of anyone *staying despite a better model elsewhere*. So Tab is not a push factor; it is the only evidenced **hold** factor. That is precisely why "table stakes — build it, don't lead with it" is the right call, and why it should not be dropped: it is cheap for us now (see the Tab section's verified core findings), and its absence is the kind that gets noticed by exactly our target user.

**5. Framework and design-system fidelity — a plausible wedge that could not be evidenced. Recorded as a hypothesis, not a finding.** *Evidence: thin — flagged rather than dressed up.* Nolan Lawson's ["The asteroid currently hitting frontend web development"](https://nolanlawson.com/2026/08/23/the-asteroid-currently-hitting-frontend-web-development/) (2026-08-23, 225 pts) argues *"The agents know React... React is heavily overrepresented in the training weights"* and *"Agent experience is starting to matter more than developer experience."* But **zero substantial sources** were found on AI tools failing to respect an *internal* design system, and **no 2026 evidence at all** on Figma→code fidelity (the best available quote is from 2025-01-22).

Worse for the intuitive pitch, the Tailwind evidence points the *opposite* way: Tailwind Labs laying off 75% of engineering ([HN 46527950](https://news.ycombinator.com/item?id=46527950), **1457 pts**) is explained in-thread as commercial-model collapse — AI got *good enough* at CSS to destroy the paid component-library business. **Do not claim "AI is bad at Tailwind."**

**And the strongest counter-argument to our entire positioning must be engaged, not ignored** — it came from Lawson's own commenters. josephg: *"Frontend development... is 'what you see is what you get'. There aren't a lot of ways a website can be invisibly broken"* ([HN 49557707](https://news.ycombinator.com/item?id=49557707)); atomicnumber3: *"Silent bugs in the backend are more dangerous and more expensive"* ([HN 49560149](https://news.ycombinator.com/item?id=49560149)). If they are right, frontend was the *first* AI target because its errors are cheap and visible, not because it is uniquely underserved — and **"frontend engineers need special AI tooling" is a weaker wedge than it looks.** The durable version of our pitch is #2 above: *the verification loop is the expensive part.* That survives josephg's objection; "AI is bad at frontend" does not.

### Two corrections to existing content in this doc

**Correction 1 — "no vendor has published a design rationale for preview-before-editor" is going stale, and the surrounding territory is no longer unclaimed.** The "Post-scaffold preview" section above (2026-09-04) concluded this was open positioning territory. That specific claim about *published rationale* was not re-checked and may still hold, but the **space around it is being occupied fast**: Antigravity 2.11.0 (2026-08-26) shipped generative UI — HTML artifacts, KaTeX and Chart.js rendered inline in chat — and 2.10.0 (2026-08-24) shipped interactive image commenting with drag-to-select regions ([antigravity.google/changelog](https://antigravity.google/changelog)), which is very close to the element-selection-to-chat flow this plan treats as differentiating. Treat "unclaimed" as having a short shelf life.

**Correction 2 — we are pinned ten minor releases behind upstream, and it is compounding.** `upstream/stable.json` pins `1.126.0` (`7e7950df8`). VS Code **1.136** shipped 2026-09-02 ([code.visualstudio.com/updates](https://code.visualstudio.com/updates)) with *Agent Merge*, multi-root workspaces carrying both Copilot and Claude agent sessions, and chat sessions moved into a separate "Agents window" — i.e. upstream has continued building in exactly the areas this plan depends on (`vs/sessions`, agent surfaces). This cuts both ways and both should be recorded: the patch-repair cost in "Real risks" #1 grows with the gap, **and** every rebase harvests agent-surface work we would otherwise build. Schedule a deliberate rebase decision rather than letting the gap widen by default.

### Where this research is thin, stated plainly so nobody treats it as settled

- **All of Reddit and X are missing**, which is where switching narratives actually live. Any conclusion above rests on Hacker News plus vendor primary sources. This is the single biggest gap; one follow-up run from an environment that can reach reddit.com would materially change confidence.
- **No market-share or DAU data exists publicly** for any of these tools. A search for any survey/market-share story above 100 points since 2026-01-01 returned zero hits. "Droves" (calmoo, 2026-04-21: *"myself and every engineer I know have switched fully from cursor to claude code"* — [HN 47855960](https://news.ycombinator.com/item?id=47855960)) is sentiment, not measurement — and it is **bidirectional**: Anamon, 2026-08-31, *"Cursor is the absolute best LLM IDE by such a ridiculously wide margin"* ([HN 49511834](https://news.ycombinator.com/item?id=49511834)).
- **Switching cost is low and falling**, which is the uncomfortable frame for all of the above: the corpus shows people moving in both directions on a timescale of days, and running several tools concurrently routed by task. Nothing in this research suggests we can build a moat out of friction. Whatever holds users has to be something they actively prefer.
- **Design-system adherence — our possible wedge — has zero evidence either way.** That is a case for primary research (interview ten frontend developers) rather than more searching.

## Real risks, tracked here so they don't get silently dropped

1. **Patch-repair is recurring work, just smaller than a merge-conflict tax.** Upstream VS Code build-system changes do break patches — the actual maintenance task is fixing failed patch hunks (VSCodium's own `update_patches.sh` documents this workflow), not resolving deep merge conflicts. Real and ongoing, but not the ~300-person-scale cost that applies only once boxcode-ide does Cursor-style deep core modifications (see "Build model" above).
2. **Specific, confirmed-blocked extensions, not just a vague "10%."** Microsoft's C/C++ extension actively checks `product.json` and refuses to run on non-Microsoft builds (confirmed, not hypothetical). VSCodium's own docs additionally list **Live Share, Python/Pylance, and Remote-SSH/WSL/Containers** as license-incompatible with forks. Re-confirm none of the target frontend-eng customer base also needs Python/Pylance before this is load-bearing.
3. **Auto-update has documented reliability issues on VSCodium** — stuck installs, update loops on macOS Homebrew, false-positive update checks on Linux (multiple open upstream GitHub issues). Adopting VSCodium's update pipeline doesn't inherit a solved problem here; budget real QA time on the updater specifically.
4. **Marketplace supply-chain trust.** VS Code forks recommending Open VSX packages has drawn documented scrutiny as a supply-chain risk surface — vet whatever ships as default-recommended extensions.
5. **License and trademark decisions are open — see `README.md`.** Not resolved by this scaffolding commit.
